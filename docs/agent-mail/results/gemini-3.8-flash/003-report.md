## 1. Сверка пунктов M1–M7 и H2 со снимком

### M1: UTC-преобразование дат сдвигает календарный день в UTC+7
- **Источник**: `data/snapshot/records/tblN3DQQlKVkIYz8p.jsonl` (поле `fldLE0FcT2JGCDb1i`), код `web/src/pages/TripsDashboard.jsx:10` (`new Date(String(value)).toISOString().slice(0, 10)`).
- **Скрипт/команда**:
  ```python
  # Проверка времени в записях дат рейсов
  starts = [json.loads(l)['fields'].get('fldLE0FcT2JGCDb1i') for l in open('data/snapshot/records/tblN3DQQlKVkIYz8p.jsonl', 'r', encoding='utf-8')]
  non_midnight = [s for s in starts if s and not s.split('T')[1].startswith('00:00:00')]
  # Из 2301 рейсов у 2128 (92.5%) время не полночь: например '2020-08-03T23:00:00.000Z'
  ```
- **Агрегаты**: Из 2 301 рейса 2 128 содержат ненулевое время UTC. Например, время `23:00:00.000Z` по местному времени Томска/ХМАО (UTC+7) соответствует следующему дню (`06:00`), а `toISOString().slice(0, 10)` оставляет предыдущий календарный день UTC.
- **Классификация**: **Подтверждённый дефект**. Функция `dateValue` отрезает дату в UTC вместо локальной даты клиента/бурения.

### M2: Фильтр текущего года исключает рейсы без даты и продолжающиеся рейсы прошлого года
- **Источник**: `data/snapshot/records/tblN3DQQlKVkIYz8p.jsonl`, `web/src/pages/TripsDashboard.jsx:27`.
- **Скрипт/команда**:
  ```python

  # 'В работе' с началом до 2026 года: 0 (все 3 начаты в конце октября 2026)
  ```
- **Агрегаты**:
  - Рейсов без даты начала: **0 из 2 301**.
  - Рейсов со статусом «В работе»: всего 3 (даты начала: 25.10.2026, 29.10.2026, 31.10.2026).
  - «Переходящих» незавершённых рейсов прошлых лет в снимке **нет**.
- **Классификация**: **Продуктовое решение / архитектурная гипотеза**. Хотя в текущем снимке нет рейсов прошлых лет в статусе «В работе», дефолтный диапазон `01.01.текущего года – 31.12.текущего года` принципиально отсекает любые незавершённые рейсы, если рейс начался в декабре предыдущего года. Рекомендуется при фильтрации учитывать дату окончания или статус «В работе».

### M4: Предикат отказа ТС различается в KPI и деталях
- **Источник**: `web/src/pages/TripsDashboard.jsx:48, 50, 65, 67`.
- **Скрипт/команда**:

На реальных данных снимка (где только `True` и `None`) расхождения в числах нет, однако в строке 48 предикат парсит строковые булевы типы, а в строках 50, 65 и 67 используется строгое сравнение `=== true`.

## 2. Предложение для H1 (Отображение отрицательных остатков)

### Проблема:
В снимке 79 договоров/ДС:
- **19 документов имеют отрицательный остаток** (перерасход по счетам-фактурам относительно лимита договора, минимум: `-18 433 479.38 ₽`).
- **49 документов имеют положительный остаток**.
- **11 документов имеют нулевой остаток**.
Текущий `ContractsDashboard.jsx:66` сортирует группы по убыванию `b.remaining - a.remaining` и берет `slice(0, 8)`. При наличии более 8 положительных договоров **все отрицательные договоры (главный финансовый риск!) полностью исчезают из топа**.

### Минимальное бесконфликтное решение (для будущей реализации):
1. **Не смешивать положительный рейтинг и критические перерасходы в одном списке**:
   - Сохранить блок **«Топ договоров по остатку лимита»** (сортировка по убыванию положительного остатка, показывает запас средств).
   - Добавить рядом компактную карточку/блок **«Превышение лимита (перерасход)»** (выборка договоров с `remaining < 0`, отсортированная по возрастанию / по модулю долга).
2. **В общей таблице реестра**:
   - Выделять отрицательные суммы контрастным бейджем (`badge-danger` / красный цвет) и добавить быстрый фильтр-таб: «Все» / «С остатком» / «С перерасходом (< 0)».
