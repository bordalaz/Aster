## 1. Документированные инструкции deploy и материалы ops

### Фактический web-root и способ обслуживания

- **Web-root: `/srv/aster`.** Служит `caddy` (HTTPS; `/api` проксирует на API `127.0.0.1:8000`; порт 5201 — веб снимка; отдельный статический корень `/srv/aster-trust` для страницы `/trust`).
- Caddyfile ставит `ops/deploy.sh` из `ops/Caddyfile` (файл не читался — точный текст директивы `root` не подтверждён; см. пробелы).
- Код проекта на сервере живёт в `~/aster` (git clone). **Сборка веба делается на ПК** (vite не работает на процессоре сервера без AVX) и копируется по ssh в `~/aster/web/dist`; затем публикация — `sudo rsync -a --delete ~/aster/web/dist/ /srv/aster/` (в `ops/deploy.sh` та же строка). `rsync --delete` означает: **старое содержимое `/srv/aster` при публикации стирается** — это ключевой факт для плана отката.

### Документированный механизм резервирования и восстановления

- **Снимки базы** (не frontend!): служба `aster-backup` (systemd) запускает `ops/backup.sh`: автоснимок раз в сутки после `BACKUP_HOUR`, каждый дамп проверяется восстановлением во временную базу со сверкой числа строк; хранение `BACKUP_DAYS` (365) дней; снимок ~9 МБ. `aster-offsite` раз в час копирует снимки в шифрованное облако (rclone, Google Drive); `BACKUP_FILES=1` — копия вложений на другой диск.
- **Восстановление базы:** `ops/restore.sh` — `pg_restore` в отдельную базу или в рабочую (`sh ops/restore.sh /backups/bd-….dump`); UI «Вернуть базу» (суперадмин) делает снимок «Перед откатом» и восстанавливает.
- **Откат из облака:** `rclone copy aster: ~/aster/backups`.

### Пробелы (не выдумывать механизм)

- **Механизм отката/резервирования frontend в документах отсутствует.** `docs/deploy.md` и `docs/backups.md` резервируют только базу и вложения; `web/dist` и `/srv/aster` не резервируются и не версионируются (`web/dist/` в `.gitignore`, не tracked в git). Единственный документированный способ «вернуть» frontend — пересобрать из старого commit и заново опубликовать.
- **Расхождение документации:** `docs/backups.md` описывает резервирование через **Docker-контейнер** (`backup`, `docker compose`), а `ops/restore.sh` использует `PGHOST=db` — дефолт для Docker. Но `docs/deploy.md` для сервера явно говорит «без Docker», всё на systemd. На сервере механизм резервирования — systemd-службы `aster-backup`/`aster-offsite`; Docker-версия описана для стенда на ПК. В `docs/backups.md` это различие не проговорено — пробел документации.

## 2. Исправленные выводы (относительно отчёта 001)

- **Наличие `web/dist` локально не доказывает соответствие сборки исходному commit `eb2d6ef`.** Дистрибутив не tracked в git, его происхождение (какой commit, когда, с какими зависимостями) не записано. В отчёте 001 это было сформулировано слишком сильно («локальная сборка соответствует рабочей папке») — верно лишь то, что рабочая папка чиста, а dist существует.
- **Различие хэшей сборок не доказывает различие исходников** и наоборот: **совпадение хэшей не доказывает совпадение исходников или commit**. Окружение сборки (версия Node/npm, зависимости из `node_modules`, переменные) может отличаться.
- **Совпадение файлов staging (`~/aster/web/dist`) и web-root (`/srv/aster`) доказывает равенство файлов на диске, но не факт, что именно их отдаёт браузеру.** Caddy может указывать на другой корень; нужно проверять HTTP-ответ.
- **Совпадение HTTP-ответа с локальными эталонными хэшами — самое сильное из доступных доказательств**, но и оно подтверждает только совпадение байтов, а не происхождение сборки: нельзя доказать, что сборка была собрана из `eb2d6ef`, если она не была собрана этим же лицом из этого commit. Происхождение сборки — **неизвестное** (нефиксируемое), и это надо фиксировать в отчётах проверки как отдельное утверждение.

## 3. Последовательность проверки только чтением

2. **Хэши web-root (равенство файлов staging и /srv/aster):**
   ```
   ssh -i C:\Users\Denis\.ssh\id_ed25519 -o IdentitiesOnly=yes -p 2222 aster-su@192.168.1.57 "sha256sum /srv/aster/index.html /srv/aster/assets/index-C63blpJD.js /srv/aster/assets/index-C0Go2whO.css 2>/dev/null"
   ```
3. **Фактический web-root:**
   ```
   ssh -i C:\Users\Denis\.ssh\id_ed25519 -o IdentitiesOnly=yes -p 2222 aster-su@192.168.1.57 "sudo cat /etc/caddy/Caddyfile; systemctl status caddy --no-pager --lines=0"
   ```
4. **HTTP-ответ (фактическое обслуживание браузеру):** на ПК, без sudo:
   ```
   curl -k https://192.168.1.57/ -o /tmp/aster-index.html
   curl -k https://192.168.1.57/assets/index-C63blpJD.js -o /tmp/aster-main.js
   curl -k https://192.168.1.57/assets/index-C0Go2whO.css -o /tmp/aster-main.css
   sha256sum /tmp/aster-index.html /tmp/aster-main.js /tmp/aster-main.css
   ```
5. **Сверка версий:** список ассетов в `index.html` (grep `'assets/[a-z0-9_-]*\.js'`) должен совпадать с локальными эталонными именами; `curl -kI https://192.168.1.57/` — заголовки (Last-Modified, ETag) — зафиксировать.

### Формулировка проверки версии (обязательная)

- **Подтверждённый факт:** HTTP-ответ сервера совпадает/не совпадает с локальными эталонными файлами по хэшам.
- **Неизвестное:** происхождение сборки — commit, из которого она собрана, если сборка не была сделана этим же агентом из этого commit. В отчёте это фиксировать как «происхождение сборки не проверено/не подтверждено», а не как «сборка соответствует eb2d6ef».

## 4. План отката (не выполнять)

### Блокер: предыдущий проверенный frontend-артефакт отсутствует

- `web/dist` не tracked в git (`web/dist/` в `.gitignore`, подтверждено `git check-ignore`), локальных архивов предыдущих сборок в проекте нет.
- Единственный кандидат на «предыдущую версию» — **текущее содержимое `/srv/aster` на сервере** (если оно ещё не совпадает с новой сборкой). Из отчёта 001: по handoff сборка загружена в `~/aster/web/dist`, но не опубликована в `/srv/aster`. Если `/srv/aster` уже содержит новую сборку, предыдущая физически удалена (`rsync --delete`) — **откат невозможен, только пересборка из старого commit.**
- Если `/srv/aster` ещё не опубликована — **перед публикацией сохранить копию** (см. ниже). Это и есть условие применимости отката.

### План отката (при условии, что копия сохранена до публикации)

1. **До публикации** (сделать один раз, сохранить список хэшей копии):
   ```
   ssh -t -i $HOME\.ssh\id_ed25519 -o IdentitiesOnly=yes -p 2222 aster-su@192.168.1.57 "sudo cp -a /srv/aster ~/aster/rollback-$(date +%Y%m%d-%H%M%S)"
   ```
2. Зафиксировать хэши копии: `sha256sum ~/aster/rollback-*/index.html ~/aster/rollback-*/assets/index-C63blpJD.js` — записать в отчёт.
3. **Откат** (если новая версия не прошла QA или не работает):
   ```
   ssh -t -i $HOME\.ssh\id_ed25519 -o IdentitiesOnly=yes -p 2222 aster-su@192.168.1.57 "sudo rsync -a --delete ~/aster/rollback-<дата>/ /srv/aster/"
   ```
4. **Проверка после отката:** те же curl-команды из п. 3 проверки; HTTP-ответ должен совпадать с сохранённой копией по хэшам.

### Условия применимости отката

- Копия сохранена **до** публикации и не была удалена/изменена (это единственный источник предыдущего frontend).
- Caddy отдаёт именно `/srv/aster` (подтверждено п. 3 проверки).
- Список хэшей копии сохранён и проверен (иначе копия сама неподтверждаема).
- Если `/srv/aster` уже содержит новую сборку — откат невозможен (блокер), только пересборка из старого commit и повторная публикация.
