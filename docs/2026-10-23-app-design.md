# Спецификация: своё приложение вместо Airtable «Воркспэйс гидроканал»

Версия: черновик 1, 2026-10-23. Основа — `docs/airtable-analysis.md` (таблицы, автоматизации, формулы, объёмы, виды).
Пометки: **[решено]** — решение пользователя; **[моё решение]** — выбор автора спецификации, можно оспорить; **[вопрос]** — ждёт ответа.

## 1. Зачем

Уйти с Airtable на свой сервер (Synology NAS в офисной сети), сохранив привычную работу: таблицы как в Airtable, виды, фильтры, формы. Логика, которая сейчас размазана по автоматизациям и формулам, переезжает в код и становится надёжнее (без рассинхронов счётчиков и cron-скриптов).

Успех: команда (~50 человек) работает в новом приложении каждый день, Airtable отключён, цифры (наработка, дефектоскопия, остатки договоров, расход ЗИП) совпадают с Airtable или отличаются только там, где в Airtable была ошибка (см. §8).

## 2. Цели, не-цели, анти-цели

**Цели**
- Все 25 рабочих таблиц и их данные (~40 тыс. записей + вложения) перенесены без потерь.
- Интерфейс «±как у Airtable» **[решено]**: сетка с правкой в ячейке, карточка записи со связями, виды с фильтрами/сортировкой/группировкой/скрытием колонок, формы ввода.
- Виды Airtable перенесены автоматически (конфиг есть в API).
- Роли и права; read-only ссылки на один вид/экран или на всё приложение **[решено]**.
- 6 автоматизаций заменены кодом (§6).

**Не-цели (v1)**
- Конструктор таблиц/полей для пользователей из интерфейса (структуру меняет разработчик миграцией). **[моё решение]**, см. вопрос В2.
- Расширения Airtable (blocks), Gantt, графики — во v1 нет; отчёты/графики — отдельный этап.
- Выключенные автоматизации («Отчет недельный», «Авто спецификация ЗИП», «Замена стейва») — не переносим без запроса.
- Совместная правка в реальном времени (курсоры других людей). Достаточно: при сохранении проверить, что запись не изменили параллельно.

**Анти-цели (провал, даже если «работает»)**
- Сетка тормозит на 13–14 тыс. строк (Ведомость ЗИП) — неприемлемо.
- Потеря или искажение данных при переносе, потеря вложений (фото ЗИП, журнал).
- Расхождение вычисляемых цифр с Airtable без объяснения.
- Нет резервных копий — один диск в NAS без бэкапа = провал.
- Приложение, которое может поддерживать только автор: нужна понятная структура и инструкция по обновлению.

## 3. Ограничения

- **Сервер [решено]:** Synology DS918+ (Celeron J3455, 4 ГБ ОЗУ, план — 8 ГБ), Docker через Container Manager, проводная LAN. Диск один (WD Purple 4 ТБ) — рекомендовано: второй диск (SHR-1/RAID1), Hyper Backup на внешний носитель/облако. DSM версия — уточнить (NAS включится 2026-10-24).
- **Бюджет памяти:** всё приложение ≤ ~1,5 ГБ ОЗУ (Postgres ~512 МБ shared_buffers 256 МБ, backend ~300 МБ, остальное — NAS).
- **Разработка:** ноутбук Windows, i5-8250U / 16 ГБ; Docker Desktop для локального запуска.
- **Airtable API:** 5 запросов/с на базу; ссылки на вложения живут ~2 ч — качать сразу после получения записей.
- **Часовой пояс:** Asia/Tomsk (как в cron Airtable).
- Язык интерфейса — русский.

## 4. Архитектура [решено: стек на выбор автора → выбран]

```
Браузер ── HTTPS ──> Caddy (статика React + reverse proxy)
                        └── /api ──> FastAPI (Python 3.12)
                                        ├── PostgreSQL 16
                                        ├── файлы вложений (том NAS)
                                        └── фоновые задачи (в том же процессе: APScheduler) → SMTP
```

Docker Compose, 3 контейнера: `db`, `api`, `web`. Тома: `pgdata`, `files`, `backups`.

- **Backend [моё решение]:** FastAPI + SQLAlchemy 2 + Alembic (миграции схемы), Pydantic. Один процесс, фоновые задачи внутри.
- **Frontend [моё решение]:** React + TypeScript + Vite. Сетка — библиотека с виртуализацией строк и лицензией MIT/бесплатной для коммерческого использования (кандидаты: TanStack Table + TanStack Virtual, Glide Data Grid). Важно: группировка и правка в ячейке — AG Grid Community не подходит (группировка только в платной версии). Финальный выбор — за разработчиком после быстрого прототипа на Ведомости ЗИП.
- **HTTPS:** самоподписанный/внутренний сертификат или сертификат Synology; зависит от В1.

## 5. Модель данных

### 5.1 Принцип [моё решение]
Каждая таблица Airtable → **настоящая таблица PostgreSQL** с типизированными колонками (не JSON-мешок). Плюс слой метаданных, который описывает таблицы для универсального интерфейса.

- Ссылки 1—N → внешний ключ. Ссылки N—N → связующая таблица. Где в Airtable N—N, а по смыслу 1—N (Скважина↔Куст) — делаем 1—N, конфликты в данных показать в отчёте миграции.
- singleSelect → справочная таблица значений (id, название, цвет, порядок) — чтобы сохранить цвета и порядок вариантов, как в Airtable. multipleSelects → связующая таблица.
- Вложения → таблица `attachment` (запись, поле, имя, тип, размер, путь на томе `files`) + превью для картинок.
- Первичное поле (ID_Работы, ID_Рейса, ID_Оборудования…) → генерируемая колонка или вычисление в представлении.
- Каждая таблица: `id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `airtable_id` (для повторной миграции и сверки).

### 5.2 Метаданные (для универсального UI)
- `app_table` — имя, иконка, порядок, первичное поле.
- `app_field` — таблица, колонка/выражение, подпись, тип отображения (текст, число, дата, select, связь, вложение, формула…), формат, редактируемо ли.
- `app_view` — таблица, тип (grid, form, kanban, calendar, gallery, timeline), владелец (личный/общий), конфиг JSON: фильтры, сортировки, группировки, видимые колонки, ширины, порядок.
- Метаданные заполняет миграция из схемы Airtable; дальше правит разработчик (поля) и пользователи (виды).

### 5.3 Вычисляемые поля [моё решение]
- Формулы, lookup, rollup, count → **SQL-представления** (`<таблица>_v`), считаются при чтении. При 40 тыс. записей это быстро; если какая-то тяжёлая — материализованное представление с обновлением после записи.
- «Год/месяц/№ + месяц» не хранить — выражения в представлениях.
- Функции rollup, которые API не отдал (список — в анализе), восстанавливаются по скриншотам пользователя и **проверяются сверкой**: значения из Airtable сравниваются со значениями из представления по каждой записи (§7.3).

## 6. Логика (замена автоматизаций)

| Airtable | В приложении |
|---|---|
| Автоматическая наработка | `Циркуляция после ТО` = сумма циркуляции завершённых и обработанных рейсов прибора после даты последнего ТО — **вычисляется**, не хранится. Поле «Добавлено в оборудование» больше не нужно. [моё решение] Перенос: сверить посчитанное с текущим значением счётчика, расхождения — в отчёт. |
| Дефектоскопия 180 дней | `Срок НК` = «Истёк», если последняя дефектоскопия старше 180 дней (по дате Asia/Tomsk). Вычисляемое, без cron. |
| Сборка → примечание | Связь «оборудование в сборке со статусом Текущие». Тег `WPR N` показывается вычисляемо (номер резистивиметра сборки). Текст Примечания не трогаем; старые теги WPR из Примечаний при миграции удалить. [моё решение] |
| Отправка перемещений на почту | При отметке «Отправляем?» — письмо через SMTP (те же поля: дата, откуда/куда, инв. номера, наименования, транспорт, причина). Адресаты и SMTP — в настройках админа. Отправка ровно один раз, факт отправки хранится. |
| Cope&Paste photo ЗИП | Загрузка фото прямо в карточке ЗИП, в т.ч. с камеры телефона. |
| Cope&Paste адрес хранения ЗИП | Правка Стеллаж/Полка в карточке ЗИП; быстрая форма «найти ЗИП по P/N → указать адрес». |

Кнопки «Разобрать», «Тест скрипт», «Создать записи в Ведомости ЗИП» — **[вопрос]**, пока не переносим.

## 7. Перенос данных

### 7.1 Инструмент
Скрипт на Python (часть репозитория), запускается вручную. Шаги: схема → справочники → записи (с учётом связей) → вложения → виды → сверка. Повторяемый: можно запускать сколько угодно раз на пустую базу; соответствие по `airtable_id`.

### 7.2 Исправления при переносе (из анализа §4)
- Номенклатура.«На ТО» (битый rollup) — восстановить по смыслу.
- ЗИП APS.«Период, мес.» — считать от реальных дат, не от захардкоженных 08.2023/12.2020.
- Работы подрядчики.«Год» — из даты, без select.
- Деление на ноль → пусто.
- Мусорные поля («Оборудование 2…6», «… copy») — не переносить, если пустые; иначе показать в отчёте.
- «Мастер»/«Сборщик» → связь с Персоналом (сопоставление ФИО; несопоставленные — в отчёт).
- Два «На калибровку» → одно значение.

### 7.3 Сверка
Для каждой таблицы: количество записей; для каждой формулы/rollup — значение Airtable vs значение приложения по каждой записи. Отчёт: что совпало, что разошлось и почему (исправленная ошибка Airtable или ошибка переноса).

### 7.4 Переход [моё решение, см. В3]
Репетиции на ноутбуке → репетиция на NAS → параллельная работа ~1–2 недели (Airtable — основной, приложение — пробное, данные перезаливаются) → день переключения: Airtable в read-only, финальный перенос, сверка, работа в приложении. Airtable держим ещё месяц только для чтения.

## 8. Пользователи, роли, доступ

- Вход по логину и паролю; учётки создаёт админ. Сессии в cookie. [моё решение]
- Роли: **Админ** (всё + пользователи + настройки), **Редактор** (правка разрешённых таблиц), **Читатель**. Права на таблицу: нет / чтение / правка — задаются для роли. Конкретная раскладка (кто что правит) — **[вопрос]**, по умолчанию все сотрудники — Редакторы всех таблиц, кроме финансов (Договоры, СЧФ, СЧФ 23, Работы подрядчики — только для роли «Финансы»).
- Виды: личные и общие; общие создаёт админ или редактор с правом.
- **Read-only ссылки [решено]:** на конкретный вид или на всё приложение. Ссылка = случайный токен, без логина, только чтение, отзывается админом, по желанию срок действия. Через ссылку не видно таблиц, на которые она не выдана.
- Журнал изменений: кто, когда, какое поле, было → стало. Просмотр истории в карточке записи.

## 9. Интерфейс

Порядок по важности (этапы — §11):
1. **Сетка:** виртуализация, правка в ячейке, вставка из Excel, фильтры/сортировки/группировки, скрыть/переставить/изменить ширину колонок, поиск, счётчик записей, итоги по колонке, выгрузка в Excel/CSV.
2. **Карточка записи:** все поля, связанные записи (открыть, добавить, отвязать), вложения с превью, история изменений.
3. **Формы:** ввод рейсов, работ, ремонтов, сборок, перемещений, журнала — как в текущих формах Airtable.
4. **Канбан, календарь, галерея** (фото ЗИП, журнал).
5. **Таймлайн** (графики работ), отчёты/графики.

Боковое меню: таблицы, сгруппированные по доменам (анализ §1); внутри таблицы — список видов.
Работа с телефона — **[вопрос В4]**; по умолчанию интерфейс должен быть пригоден на телефоне хотя бы для карточки, форм и фото.

## 10. Развёртывание и бэкапы

- `docker-compose.yml` + `.env` (пароли, SMTP, секрет сессий). Инструкция: установка на NAS, обновление (`docker compose pull && up -d`, миграции применяются при старте), откат.
- Бэкап: ночной `pg_dump` + копия тома `files` в `backups`; хранить 14 дней + ежемесячные. Hyper Backup забирает `backups` за пределы NAS. Проверка восстановления — раз в квартал по инструкции.
- Мониторинг минимальный: страница здоровья `/api/health`, лог ошибок.

## 12. Открытые вопросы

- **В1.** Доступ только из офисной сети или и снаружи (интернет/VPN)? Влияет на безопасность, HTTPS и read-only ссылки.
- **В2.** Нужно ли, чтобы сотрудники сами добавляли поля/таблицы, как в Airtable, или структуру меняет только разработчик?
- **В3.** Переход: параллельная работа 1–2 недели устроит, или нужен переход за один день?
- **В4.** Работают ли с телефона (цех, склад, выезд)? Что именно делают с телефона?
- **В5.** Кто что редактирует (раскладка ролей).
- **В6.** Кнопки Сборок и ЗИП — что делают.
- **В7.** Вид «Просроченная дефектоскопия» по циркуляции ≥ 7,5 ч — так задумано?
- **В8.** Местонахождение оборудования: последнее перемещение по порядку ввода или по дате?
- Скриншоты rollup (список — в анализе).
