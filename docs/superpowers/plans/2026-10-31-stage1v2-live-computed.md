# Этап 1в-2 — вычисляемые поля в API, по цепочке от сырых данных

**Почему:** в 22 из 28 таблиц первичное поле — формула (ID_Оборудования, ID_Работы…). API отдавал только хранимые поля, поэтому в сетке PR #2 закреплённая колонка ID на реальных данных пустая. Брать значения из `at_computed` нельзя: это застывший снимок Airtable, после правки он не обновится.

**Решение:** `compute_all` считает все 213 вычисляемых полей (formula, rollup, lookup, count) в порядке зависимостей (`graphlib`) от сырых данных, `at_computed` при этом не читает. Зависимости поля — его входы плюс первичные поля таблиц за связями: имя связанной записи — это её первичное поле, часто формула. `app/computed.py` держит результат в памяти процесса API. `/records` отдаёт вычисляемые поля, после PATCH (уже после commit) идёт пересчёт в фоне; более старый расчёт не перетирает более свежий.

## Результат на реальной базе (2026-10-31)

- Вся цепочка от сырых данных совпала с Airtable во всех 213 полях, кроме известного `Номенклатура.На калибровку`. Это сильнее изолированной сверки 1б-2: ошибки не накапливаются по цепочке.
- Полный пересчёт — **5,8 с**. Было 23 с: цель фильтра rollup искалась запросом к БД на каждую пару, теперь считается один раз на фильтр.
- `/records` Оборудования: первый запрос после старта 6,3 с (расчёт), дальше 0,25 с. Правка «Серийный номер» видна в `ID_Оборудования` через ~6 с.

## Ограничения (`ponytail:` в коде)

- Память одного процесса и полный пересчёт базы после каждой записи. Если появятся несколько воркеров или запись чаще раза в несколько секунд — хранить в таблице и пересчитывать только поля, зависящие от правки.
- Поля с `TODAY()` обновляются при следующей записи, а не в полночь.
- Связи (имена связанных записей) API пока не отдаёт — этап 2.
- Сетка PR #2 показывает ячейки по типу поля. Для formula/rollup/lookup нужен показ по `options.result.type`, а `{"specialValue": "NaN"}` и `{"error": "#ERROR!"}` — текстом «NaN»/«#ERROR!». Это правка в ветке PR #2.
