## 3. Вычисляемые поля

Формулы получены полностью (текст есть в ответах `get_table_schema`). Категории:
- **Первичные имена** (конкатенации): `ID_Работы = Скважина_Этап`, `ID_Рейса = Работа_№[-АРЕНДА]`, `ID_Оборудования = Наименование_№_Серийный`, `Код_Договора`, `№ Перемещения = дата: Откуда>>Куда` и т.д. → генерируемые колонки / отображаемое имя.
- **Год/месяц/«№ + месяц»** от дат — в ~15 таблицах → не хранить, считать в запросах/отчётах.
- **Метрики**: Время рейса = Конец−Начало (ч); Удельное НПВ (на 1000 ч циркуляции / 1000 м); ТОиР на час/метр; КПЗО = дней в работе / дней на балансе; КРО = дней в ремонте / дней в работе; Остаток договора = Сумма − СЧФ20 − СЧФ23; Расход ЗИП в мес., НЗ на 90 дней, Потребность.
- **Rollup/lookup/count** (~100) → SQL-представления/агрегаты.

### Конфиги rollup (сняты 2026-10-30)
70 rollup-полей. Связь, поле-источник и фильтр взяты из метаданных API (`get_table_schema` → `config.recordLinkFieldId`, `fieldIdInLinkedTable`, `filters`). Функцию агрегации API не отдаёт. Её прочитали в веб-интерфейсе: Manage fields → настройки поля → Cancel, ничего не сохраняли.
У всех 70 полей «Sort records before summarizing» выключена, порядок значений = порядок ссылок в поле-связи. Включённый фильтр («Only include… conditions») есть ровно у тех полей, где в таблице указан фильтр.

`values` — значения поля-источника у связанных записей. Если источник многозначный (lookup, связь, multiSelect), значения расплющиваются в один список.

## 4. Найденные проблемы данных (исправить при переносе)
- Номенклатура.«На ТО» — rollup невалиден (`isValid:false`): поле-источник не задано, фильтр ссылается на удалённый вариант статуса (§3).
- Фильтры «Год > 2021» в Оборудование.«Пробурено, м» и «Стоимость ТО ССК-Т» отсекают 2021 год, хотя в Заказчиках везде «≥ 2021». Возможно, это ошибка. Пока копируем как есть.
- Персонал.«Всего рейсов с APS» считает ссылки на инженеров, а не рейсы (§3, ⁵).
- ЗИП APS.«Период, мес.» — даты захардкожены `DATETIME_DIFF('08-01-2023','12-31-2020')` → расход в мес. считается неверно после 08.2023.
- Работы подрядчики.«Год» — select только до 2024.
- Деление на ноль: Заказчики (НПВ на работу, на 1000 м, на 100 ч), Персонал.«К», Оборудование.КПЗО.
- Мусорные поля: Перемещение «Оборудование 2…6», «ID_Оборудования copy/copy 2»; Ремонты ССК-Т «Оборудование 2/3».
- Дубли справочников: «Мастер» и «Сборщик» — multiSelect с ФИО вместо связи с Персоналом.
- Статус оборудования: два варианта «На калибровку» (разные id).
- Местонахождение оборудования = «последнее перемещение по порядку ввода, независимо от даты» — уточнить, нужна ли логика по дате.

## 6. Виды (views)

Публичный API отдаёт у вида только название, тип и видимые колонки (grid, `include=visibleFieldIds`); **фильтров, сортировок и группировок в API нет** (проверено 2026-10-31). Переносим скриптом то, что есть (`python -m migrate views`), остальное — вручную или по скриншотам.

Используемые типы: grid (большинство, часто с группировкой), kanban, calendar, timeline (графики работ), gallery (фото ЗИП/журнал), form (ввод рейсов, работ, ремонтов, сборок, перемещений, журнала), block (графики-расширения, Gantt).

Много видов по ролям: «Вед. инженер …», «Для цеха», «НЮ_Ремонтный цех», «ГПНХ» (по заказчику), «Для отчета ПЭО». → В новом приложении: личные и общие виды + роли.

Самые развитые таблицы по видам: Оборудование (46), Рейсы APS (25), Ремонты ССК-Т (17), Работы (16).

Замечание: вид «Просроченная дефектоскопия» фильтрует по `Циркуляция после ТО ≥ 27000 сек (7,5 ч)`, а не по дате — уточнить у пользователя.
