# Снимки базы

Как в Airtable: снимок делается сам раз в сутки и по кнопке, хранится год; снимок можно **открыть**
(посмотреть базу на тот момент, рабочая не меняется) или **вернуть к нему базу** целиком.

Раздел **«Снимки»** — меню профиля, только админам. «Вернуть базу» — только суперадмину, с подтверждением.

## Как устроено

- **Контейнер `backup`** (`ops/backup.sh`, образ `postgres:16-alpine`) делает всю работу:
  - автоснимок раз в сутки после `BACKUP_HOUR` (3:00 по `BACKUP_TZ`);
  - задания из раздела «Снимки» — ручной снимок, «Открыть», «Вернуть базу» — проверяет каждые 10 с, по одному.
- **Каждый снимок проверяется:** дамп восстанавливается во временную базу, число строк во всех таблицах
  сверяется с рабочей. Не сошлось — файл `.bad`, `ОШИБКА` в логе.
- **Хранение:** `BACKUP_DAYS` дней (365), старые стираются. Снимок ~9 МБ → за год ≈ 3,3 ГБ.
- **Список снимков и задания** — служебная база `bd_ops` (её создаёт `backup`). Откат рабочей базы её не трогает.
- **Ручной снимок** — не чаще раза в час.
- **«Открыть снимок»:** снимок восстанавливается в базу `bd_snapshot`, её показывает экземпляр API
  `snapshot-api` (порт 8001) — та же программа, **только чтение** (запись не примет и сама БД). Веб снимка —
  порт 5201 (`npm run dev:snapshot`), сверху плашка «Снимок … — только просмотр». Вошедшие остаются вошедшими.
  Открыт один снимок за раз: открыть другой — заменит.
- **«Вернуть базу»:** сначала снимок текущего состояния («Перед откатом» — откат можно отменить тем же способом),
  потом снимок восстанавливается в отдельную базу и подменяет рабочую. Не восстановился — рабочая не тронута.
  API сам перезапускается на возвращённой базе (около минуты недоступен). Всё, что изменили после снимка, пропадает.
- **Вложения в снимки не копируются и не нужны:** файлы не удаляются, даже когда их убирают из записи, —
  открытый или возвращённый снимок находит свои файлы на месте. От поломки диска вложения защищает
  `BACKUP_FILES=1` (одна копия в `BACKUP_DIR/files`, каждую ночь докопируются новые) — **только если `BACKUP_DIR`
  на другом диске**: копия на том же диске место тратит, а от поломки не спасает.

**Настройки** (`.env`): `BACKUP_DIR`, `BACKUP_HOUR`, `BACKUP_DAYS`, `BACKUP_TZ`, `BACKUP_FILES`, `SNAPSHOT_URL`
(адрес веба снимка, по умолчанию тот же хост, порт 5201).
На NAS `BACKUP_DIR` — **другой диск или том**: снимки на том же диске погибнут вместе с базой.

## Команды

```
docker compose exec backup sh /ops/backup.sh now        # снимок из консоли
docker compose logs backup                              # лог снимков и заданий
docker compose exec backup sh /ops/restore.sh /backups/bd-2026-11-03_030000.dump bd_test   # проверить дамп в отдельной базе
```

Если программа не запускается совсем (откатить из интерфейса нельзя):

```
docker compose stop api
docker compose exec backup sh /ops/restore.sh /backups/bd-2026-11-03_030000.dump      # заменит данные bd!
docker compose start api
```

В Git Bash на Windows перед командами с `/ops`, `/backups` добавлять `MSYS_NO_PATHCONV=1`, иначе пути подменятся.
